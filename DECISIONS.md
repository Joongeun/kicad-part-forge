# Decisions

Locked decisions that should not be silently relitigated. Newest last.

---

## 2026-08-17 — Phase 0a: own the S-expression emitter (GATE PASSED)

**Decision.** Build and own the S-expression parser/writer. Do not depend on
`kiutils` or `KicadModTree`.

**Evidence.** `src/kifab/emit/sexpr.py` + `tests/test_roundtrip.py`, run against
the KiCad 9.0.4 install:

- Semantic round-trip (no data loss) on **400 footprints + 10 symbol libraries** — pass.
- Byte-exact idempotence on **400 footprints** — pass.
- Byte-exact on every node shape we generate — pass.
- `kicad-cli fp upgrade --force` accepts our output (exit 0); `fp export svg` renders it.

**Measured limitation, accepted deliberately.** We do *not* byte-match arbitrary
third-party files. KiCad's shipped libraries are not uniformly formatted (written
by several generators over many years), and even within `kicad-cli`-canonicalised
output the `pts` packing rule could not be reduced to a consistent formula: across
486 width-bound samples the longest line KiCad *kept* was 122 chars while the
shortest it *rejected* was 113, so it is not a pure column limit. The only clean
invariant found was a hard ceiling of **8 points per line**.

This is not a requirement of anything in the project. The requirements are no data
loss (enforced across the corpus) and `kicad-cli` acceptance (enforced per build).

## 2026-08-17 — `kicad-cli fp upgrade` is a canonicaliser, not just a validator

**Decision.** Treat `kicad-cli` as the source of truth for canonical KiCad 9 form,
and encode its rules in the emitter rather than guessing them.

**Why.** Feeding it a minimal hand-written footprint and diffing what came back
produced the canonical-form spec directly. Rules it enforced:

| Rule | Detail |
|---|---|
| `generator_version` | `(generator_version "9.0")` is required alongside `(generator ...)` |
| Mandatory properties | All four of Reference, **Value, Datasheet, Description** always present, even when empty |
| UUIDs | Every property, `fp_line`, `fp_poly`, and `pad` carries a `(uuid ...)` |
| Pad layer order | Canonical order is `"F.Cu" "F.Mask" "F.Paste"` — **not** Cu/Paste/Mask |
| Trailer | `(embedded_fonts no)` closes the footprint |
| `attr` placement | Moves to after the property block |

## 2026-08-17 — Phase 0b: own the IPC-7351B maths (GATE PASSED)

**Decision.** Implement IPC-7351B land-pattern calculation ourselves, vendoring
KiCad's rule *data* (`ipc_7351b.yaml`) but not their code. Proceed with the
IR-centric architecture; do **not** fall back to vendoring the generator wholesale.

**Evidence.** `src/kifab/ipc/` + `tests/test_ipc.py`. Fed the same input dimensions
the KiCad library team publishes, our computed land geometry matches the shipped
footprints **exactly** (≤1e-4 mm) across three IPC device classes:

| Package | Class | length × width @ centre |
|---|---|---|
| LQFP-48_7x7mm_P0.5mm | gullwing, small pitch | 1.475 × 0.30 @ 4.1625 |
| SOIC-8_3.9x4.9mm_P1.27mm | gullwing, large pitch | 1.95 × 0.60 @ 2.475 |
| QFN-32-1EP_5x5mm_P0.5mm | flat no-lead | 0.875 × 0.25 @ 2.4375 |
| SOT-23-5 | gullwing, large pitch | 1.325 × 0.60 @ 1.1375 |

**Recovered constants.** IPC's fabrication allowance **F = 0.10 mm** and placement
allowance **P = 0.05 mm** are not stated in any upstream config file. They were
recovered by solving against LQFP-48 and then confirmed against every other case
above. They live in `kifab.ipc.rules` as named constants so drift surfaces as a
test failure rather than silently wrong pads.

## 2026-08-17 — The official library is NOT a perfectly reliable oracle

**Decision.** When computed geometry disagrees with a shipped footprint,
investigate before assuming our arithmetic is wrong. Compare against the inputs
the footprint was *generated from*, not merely the current size definitions.

**Why.** `SOT-23` does not match its own current size definition. Feeding today's
`sot.yaml` (`lead_len: 0.40 .. 0.60`) gives Gmin=0.35; the shipped footprint
implies Gmin=0.40. Feeding `lead_len: 0.40 .. 0.55` reproduces the shipped file
exactly — so it was generated before that dimension was revised and never
regenerated. `SOT-23-5`, generated by the same script, matches us perfectly.

**Consequence.** Kept as `test_shipped_sot23_is_stale_not_our_maths` rather than
deleted, so the reasoning stays in the suite. If upstream regenerates SOT-23 the
test fails and tells us to promote it back into the main comparison set.

## 2026-08-17 — UUIDs are derived, never random

**Decision.** Generate every `(uuid ...)` deterministically as a UUIDv5 over
`(part identity, element kind, element index)`. Never call `uuid4()`.

**Why.** KiCad requires UUIDs on most elements, but random ones make output
non-reproducible: the same IR would emit a different file on every run, so
golden-file tests could never be byte-compared and every regeneration would show
a spurious diff in git. Deriving them keeps the pipeline a pure function of the
IR, which is what makes the golden-file gate meaningful.

**Consequence.** Two different parts never collide (identity is in the hash), and
regenerating an unchanged part is a no-op in version control.

## Phase 1 — Phase 1: the Part IR stores conventions, not coordinates (2026-08-17)

- **Lead.** Pins declare a `side` + optional `slot`; packages declare datasheet dimensions. Coordinates are computed by the emitters, never stored in the IR.
- **Why.** Three things fall out of it that a coordinate-based IR cannot give: house style (grid, pin length, text sizes, silk offsets) is a one-place change; an off-grid pin is *inexpressible*, so KLC's 100 mil rule holds by construction; and the YAML diffs as a pin table rather than a drawing.
- **Escape hatches, named so review can see them.** `CustomPackage` (lands stated directly — also the target an EasyEDA/vendor importer lands in), `SymbolStyle.body_width/body_height`, and `Pin.length`. An IR that cannot represent its inputs is not a contract, so the escape hatch is deliberate; making it conspicuous is what stops it becoming the default.
- **`extra="forbid"` everywhere.** A typo'd key that is silently ignored ships a part with a wrong value. It must fail loudly.
- **The IR cross-checks its two halves.** Every symbol pin must have a matching footprint pad and vice versa. A symbol/footprint pair that disagrees about pin numbers routes a board wrong and nothing downstream notices.

## Phase 1 — Emit KiCad's canonical form, not merely something it accepts (2026-08-17)

- **Lead.** Both emitters produce output that `kicad-cli … upgrade --force` rewrites **byte-for-byte identically**, apart from the `(generator …)` token it stamps with its own name. `tests/test_conformance.py` asserts exactly that, on every part in the corpus.
- **Why this is stronger than "it parses".** A file KiCad merely accepts still gets rewritten the first time someone opens it in the GUI, so a part edited by hand and a part regenerated from the IR would show a diff of pure noise. Being a fixed point makes that diff meaningful.
- **What it cost.** Three ordering rules, discovered by diffing: footprint `fp_line`s are sorted by start point; symbol pins are sorted by (x ascending, y descending); user properties (`Manufacturer`, `MPN`) come *before* the `ki_*` ones. None of these are documented anywhere — they were measured.
- **Symbol form, established the same way as the Phase 0 footprint form.** `(generator_version "9.0")`; per symbol `(exclude_from_sim)(in_bom)(on_board)` before the properties; Reference/Value/Footprint/Datasheet/Description always present; `(effects (font (size …)))` on every pin name and number; `(embedded_fonts no)` closing each symbol. Symbols carry **no UUIDs** — that is KiCad's rule, not an omission.

## Phase 1 — Pin grid beats body symmetry (2026-08-17)

- **Lead.** Symbol bodies are sized so that *half* the width and *half* the height are whole grid steps, and pins are placed at whole grid steps from the origin. When a side has an even number of pins the group therefore sits half a step off-centre.
- **Why.** KLC requires pins on the 100 mil grid and wiring depends on it; body symmetry is cosmetic. Centring the group instead would put every pin on a 50 mil offset whenever the pin count is even — which is what KiCad's own `Device:R` does, but not what its 48-pin `STM32F103C_8-B_Tx` does (checked: all 48 pins on 100 mil, body symmetric, some pins outside the body).
- **Consequence.** `SymbolStyle.body_width`/`body_height` overrides can break the guarantee, so their field docs say so. `tests/test_emit_symbol.py` holds the invariant for pin counts 1..26.

## Phase 1 — Chip (two-terminal) IPC maths is NOT owned yet — deferred, not forgotten (2026-08-17)

- **Lead.** `parts/BLM31PG601SN1L.yaml` (1206 ferrite bead) uses `family: custom` with lands stated directly, not computed.
- **Why.** The vendored `vendor/ipc/ipc7351B_2terminal.yaml` tables exist, but a spike against the shipped `R_0805_2012Metric` did **not** reproduce its geometry from any plausible reading of the IPC-SM-782 body dimensions: solving for Zmax works (L = 2.00 ± 0.10 gives 2.85 exactly), solving for Gmin does not — the shipped 0.80 needs an inner-span input the size tables do not state. KiCad's chip generator evidently takes the lead *separation* S directly rather than deriving it from a termination length.
- **Consequence.** Do not add a `chip` family until that input is identified and the result is diffed against the shipped 0402/0603/0805/1206 footprints, the same gate Phase 0b applied to gull-wing. Emitting plausible-but-unverified chip pads is exactly the silent failure this project exists to prevent.
- **Also deferred from Phase 1:** no-lead (QFN/DFN) families and exposed pads, non-rectangular symbol graphics, and thermal/paste-relief options on pads.

## Phase 2 — Package identity, not body size, decides a footprint match (2026-08-17)

- **Lead.** A T0 footprint result is `confident` only when package identity is **established**: family, perimeter pin count, pitch, body and exposed-pad presence are all stated on both sides and agree, and no decisive attribute disagrees. An attribute nobody stated blocks confidence exactly as hard as one that disagrees — "we could not tell" is not "it matches".
- **Why.** KiCad ships `DFN-12-1EP_2x3mm_P0.45mm_EP0.64x2.4mm` (DDB, Linear DWG 05-08-1723). The LTC5552 UDB package is a 12-lead QFN, same 2x3 mm body, LTC DWG 05-08-1985 — a different lead frame, a different land pattern. Ranking on body size hands back a wrong footprint that looks right in the browser and in 3D, and scraps a board.
- **The discriminators, and which are measured.** family (from name + description, canonicalised by longest-suffix so HVQFN→QFN and UDFN→DFN, but DFN never→QFN); **edge count, measured from pad positions** — a DFN has lands on 2 edges, a QFN on 4, and this holds even when the name lies; perimeter pin count; pitch (declared in the KiCad name, else measured); body envelope, orientation-independent; exposed-pad presence and size; manufacturer drawing number when either side states one.
- **No score can outvote a decisive mismatch.** The DDB look-alike scores *positively* against a fully specified UDB query — five of eight attributes agree. Had confidence been a threshold on a score, that is the case that would have shipped the wrong footprint. Held by `tests/test_package_id.py::test_no_score_can_outvote_a_decisive_mismatch`.
- **Two measured traps found while building it**, both of which made a DFN read as a four-sided package: unnumbered pads (paste-relief apertures over the exposed pad — the real DDB file has two, which made it measure as 14 pins on 4 edges), and `*_ThermalVias` variants (vias carrying the exposed pad own number). Both are now excluded/merged, with regression tests against the real files.

## Phase 2 — Confident vs review is a data-structure split, not prose (2026-08-17)

- **Lead.** `MatchSet` carries two separate lists, `.confident` and `.review`, and deliberately exposes **no combined accessor**. `.best` returns the first confident match or `None`; it never falls through to a near miss. Every candidate also carries its `basis` (why it is where it is) and the per-attribute `evidence` behind that verdict.
- **Why.** A single ranked list invites `results[0]`, and the near miss is exactly the thing that ranks highly. Making the unsafe result reachable only by naming `.review` turns a judgement call into an API-surface constraint.
- **Three bases for confidence, never a score threshold.** `EXACT_NAME` (the caller named the footprint), `SYMBOL_PROVENANCE` (a confidently matched symbol Footprint property names it — KiCad librarians already paired them; **demoted to review when a stated package hint contradicts it**), and `PACKAGE_IDENTITY` (every identity attribute stated and agreeing).
- **The review list is ranked on confusability, not on score.** Confusability counts agreement across the *visible* geometry only — pins, pitch, body, exposed pad, EP size — deliberately excluding family and edge count, because those are what a dangerous near miss gets wrong. Ranking by score buried the DDB footprint at position 39 behind unrelated connectors; ranking by confusability puts it first, which is where a human needs it.

## Phase 2 — The index is a derived cache: incremental by file stamp, disposable (2026-08-17)

- **Lead.** SQLite + FTS5 at `~/.cache/kifab/index.sqlite3`, one row per footprint and per symbol, refreshed by comparing each file `(mtime, size)`. Measured on this machine: **cold build 42 s for 15,189 footprints + 22,395 symbols (40 MB); steady-state refresh 0.25–0.3 s** with zero rows touched.
- **Why not parse per query.** 37k items is ~36 s of parsing. A resolver nobody waits for is a resolver that gets skipped in favour of generating a duplicate part, which is the failure this tier exists to prevent.
- **Package identity is extracted once into columns**, not re-derived from the name at query time. That is what lets the resolver reject on measured geometry rather than on a string.
- **`synchronous = OFF` is deliberate.** The index is derived from files that still exist; trading crash durability for build speed costs nothing we cannot regenerate. It took the cold build from 184 s to 42 s together with the indexing fix below.
- **Uniqueness is keyed on the file path, not the library nickname.** Two `.pretty` directories can share a stem (a project library called `Package_SO.pretty` next to KiCad own). Keying on the nickname made every refresh delete the other directory rows and re-add its own — the index never converged, and every search paid a full re-parse. Held by `tests/test_index.py::test_two_libraries_with_the_same_nickname_do_not_evict_each_other`.

## Phase 2 — Adoption lands in the IR, and restyles the symbol (2026-08-17)

- **Lead.** `kifab adopt` writes `parts/<MPN>.yaml`. Pads are lifted **verbatim** into a `custom` package (the IR declared escape hatch, so the reuse is visible in review); the symbol is **re-laid-out in house style** — the IR stores a pin side and slot, never coordinates, so a donor whose pins were grouped by function comes back as a rectangle in positional order. `adopt()` reports that in the file header.
- **Why not just point at the existing library.** Reuse must not be a dead end. A part outside the IR gets no house style, no validators, no correction path and no Part-DB registration. Adopting keeps it a normal citizen: it rebuilds, it passes the same `kicad-cli` gate, and a wrong pin is a one-line edit.
- **Adoption is not a hole in the IR pin/pad cross-check.** A symbol and footprint that disagree about pin numbers raise `AdoptionError` rather than being written out. Adopting a footprint with no symbol requires `--pins-from-pads`, which writes an explicitly-unverified stub (`type: unspecified`, no names) and says so in a `# NOTE:` line.
- **Bug found and worked around, not patched silently:** `Pin.number` coerces an int from YAML, `Pad.number` does **not** (pydantic v2 will not coerce int→str). So `number: 1` is valid for a pin and invalid for a pad — the same key behaving differently in the same file. Adoption now quotes any numeric-looking string it emits. The IR asymmetry itself is left as-is for a later phase to decide on deliberately; `tests/test_adopt.py::test_the_written_yaml_reloads_and_builds` is the regression.

## Phase 3 — One rule for pad and pin numbers: coerce the integer, refuse the fraction (2026-08-17)

- **Lead.** Both `Pin.number` and `Pad.number` are typed `str` and both **coerce a bare YAML integer** to one. `number: 1` and `number: "1"` are now equally valid, for pins and pads alike. A non-integral value (`number: 1.5`) is **refused**, not truncated.
- **The defect this closes.** Phase 2 reported it: `Pin.number` coerced, `Pad.number` did not (pydantic v2 will not coerce int→str), so the same key behaved differently in the same file and the error message could not explain why. `kifab adopt` had to work around it by quoting every numeric-looking string it emitted.
- **Why coerce rather than require quotes everywhere.** The IR's reviewable artefact is a hand-written pin table. Requiring `number: "1"` taxes the overwhelmingly common case (an integer) to serve the rare one (BGA `A1`, exposed pad `EP`), and a forgotten quote is a validation failure on a file that is obviously correct to a human. The runner-up — drop the coercion from `Pin` so both are strict — was rejected on exactly that: it makes the corpus noisier to write and buys no safety, because the string type is preserved either way.
- **Why 1.5 is an error rather than pad 1.** Truncating is the silent-wrongness this project exists to prevent. It is a typo in every real datasheet.
- **Blast radius, all of it.** New `src/kifab/ir/designator.py` holds the one rule; `pin.py` and `package.py` both call it. `parts/BLM31PG601SN1L.yaml` had the only quoted pad numbers in the corpus and now writes them unquoted, which is the demonstration that the asymmetry is gone. `resolve/adopt.py` still quotes numeric strings — no longer because it must, but because the quotes say out loud that the column is a string; its comment now says so. **No emitted bytes changed, so no golden file was regenerated.** Regressions: `tests/test_ir.py::test_pad_number_reads_exactly_like_a_pin_number` and `::test_a_fractional_number_is_refused_rather_than_truncated`.

## Phase 3 — Severity is enforced in one place, and 'skipped' is not 'passed' (2026-08-17)

- **Lead.** Three severities, one predicate. **error** = wrong under any house style, blocks the build. **warning** = questionable but buildable, never blocks unless `--strict`. **info** = a note, including "this check could not run", and blocks *nothing, ever*. `Report.ok(strict=…)` is the only place that decides, and `Severity.blocks` the only predicate; nothing else in the codebase re-implements the verdict.
- **Why the third level exists.** An unrunnable check must never look like a passing one. With kicad-cli absent, the conformance gate emits an `info` finding saying it did not run — so a CI log that says "OK" while the strongest gate never executed is still readable as such (`-v` prints them). Held by `tests/test_validate.py::test_the_conformance_gate_reports_a_skip_rather_than_a_pass`.
- **`--strict` promotes warnings and nothing else.** `scripts/verify.sh` runs `kifab check parts/ build/ --strict`, because for *our own* corpus a convention deviation is a defect. Ad-hoc checks of third-party files are exactly the case `--strict` is not for.
- **Every rule declares its own severity, and heuristics are always warnings.** A rule that needs a threshold cannot be an error, because the threshold is a judgement. Errors are all pass/fail on a measurement: copper of two nets touching, a pad outside the courtyard, a symbol and footprint disagreeing about pin numbers, a file KiCad's parser rejects.

## Phase 3 — Validators read the emitted file; the IR layer is for contradictions only (2026-08-17)

- **Lead.** Geometry and KLC rules read the **emitted file**, never the IR. An IR part is checked by rendering it in memory and reading the result back (`validate.check_part`). Only `validate/schema.py` reads a `Part`.
- **Why.** Silkscreen, courtyard, layer names and text sizes do not exist upstream of the emitter — a silk line lying on a pad is a defect that is *not expressible* in the IR. Writing those rules against the IR would mean re-deriving the drawing inside the linter, i.e. testing the emitter against a second copy of itself. Reading the file also means the same rules apply to a footprint with no IR behind it: an adopted KiCad part, a vendor download, an EasyEDA import (Phase 4).
- **What the IR layer is therefore for:** contradictions between well-typed statements. A lead span narrower than the body it wraps (transposed dimensions — every land ends up under the plastic), a pin named `GND` typed `output`, a footprint *name* stating a pitch its geometry does not have. Those are invisible in the file, because the emitter faithfully draws the wrong thing.
- **Consequence for `kifab check`.** It takes a part YAML, a `.kicad_sym`, a `.kicad_mod`, a `.pretty` directory or a tree of them, and the cross-file rule (symbol/footprint pin-set agreement) runs whenever both halves are present — including on a built library, matched through the symbol's `Footprint` property.

## Phase 3 — Lint thresholds are measured against the corpus, not quoted from a spec (2026-08-17)

- **Lead.** Every geometry threshold is a named constant whose value was **measured against the shipped corpus**, not taken from a document. The measurements, and what they cost:
- **`MIN_PAD_GAP = 0.10 mm`** (warning below; overlap is an error). The first value tried was 0.15, the usual class-2 fab minimum. It fired on **252 pad pairs across Package_QFP**, every one of them at exactly **0.14 mm** — the IPC-7351B result for a 0.4 mm-pitch QFP. A linter that warns on the standard land pattern for a standard package trains people to ignore it. 0.10 sits below every land pattern in the corpus.
- **`SILK_PAD_CLEARANCE = 0.20 mm`, measured edge-to-edge and Euclidean** (KLC F5.1). This is deliberately stricter than the shipped corpus at pad *corners*: the official chip footprints trim silk only along the segment axis, so `Resistor_SMD` shows diagonal clearances down to 0.03 mm. Our own emitter grows the pad box in both axes, so its output clears 0.2 mm in every direction and never fires. Kept as a warning, and this is one of the cases where the official library is not the oracle (see the Phase 0 lock).
- **`COURTYARD_MIN_EXCESS = 0.05 mm`** — far below the IPC nominal 0.25 so a legitimately dense footprint stays silent. It fired **zero times** across the corpus, which is the evidence it is not a nuisance rule.
- **`PIN_GRID = 2.54 mm`**, `TOL = 1e-4 mm`. The tolerance exists because the emitter places silk *exactly* on the clearance boundary; `0.2 - 0.2` landing at -1e-16 must not be a finding. Held by `test_silk_at_exactly_the_clearance_limit_is_silent`.
- **Exactness where it would have been easy to approximate.** Pad-to-pad distance is computed between true oriented rectangle outlines (segment/segment plus containment), not circumscribing boxes: a rotated pad's circumscribing square over-states its copper and would invent shorts. Cost: a sweep in x so a 2000-ball BGA stays O(n log n) — `Package_BGA` went from a >2 min timeout to under a second.

## Phase 3 — Port the KLC rules that catch defects; record the skipped ones with reasons (2026-08-17)

- **Lead.** KLC is ported selectively: the rules where a violation is a *defect* rather than a matter of taste, and where the check is decidable from the file alone. What was left out is enumerated in `klc.SKIPPED` **with its reason**, and a test asserts the reasons are actually written.
- **Implemented.** F3.1 (name is a library item name), F5.1/F5.2/F5.3 (silk 0.12, fab 0.10, courtyard 0.05 line widths; F.Fab body outline and `${REFERENCE}`; silkscreen Reference text 1.0/0.15; the four canonical properties), F6.2 (pin-1 indicator), F7.1 (`(attr …)` must match the pads that are there), F9.1 (3D model path resolves off this machine). Symbols: S3.1 (name), S4.1 (100 mil pin grid), S4.2 (pin length), S4.3 (pin text size), S6.3 (the five canonical properties).
- **Skipped, and why — the interesting ones.** *F4.x per-family land geometry*: that is what the IPC-7351B module computes and what `tests/test_ipc.py` already diffs against the official corpus; a lint rule would test the same arithmetic twice. *F3.x family naming grammar*: hundreds of special cases, mostly taste — the part of it that catches defects (a name whose stated pitch or pin count contradicts the geometry) is implemented instead as `SCH009`. *S5.x "Value must equal the symbol name"*: **false on correct parts** — `parts/BLM31PG601SN1L.yaml` sets `600R@100MHz`, which is right for a generic part. A rule that fires on correct parts trains people to ignore the linter, which costs more than the rule is worth. *F2.x 3D model correctness, F7.2 THT pad shapes, F8.x paste/thermal relief*: no oracle, or nothing to check until QFN/DFN and through-hole packages are generatable.
- **Two Phase 2 traps are handled in the parse layer, once, rather than in each rule.** Unnumbered pads are paste apertures and carry no net. `*_ThermalVias` vias are recognised either by sharing a number with an SMD land **or by lying wholly inside one** — TI's `Texas_RGY_R-PVQFN-N16` numbers its via net separately, so the number test alone was not enough. Pads are also only compared when their **copper layers intersect**: a `*_ThermalVias` variant puts a B.Cu land under the exposed pad that overlaps every perimeter land in plan view and touches none of them. Each of the three, unhandled, produced dozens of false errors on the shipped corpus.
- **Calibration result, for the record.** After those fixes the linter reports **12 errors across 7 files in the 653-footprint `Package_DFN_QFN`**, 11 in one `Package_SO` file, 1 in `Capacitor_SMD`, and **zero** in `Package_QFP`, `Package_BGA`, `Resistor_SMD`, `Package_TO_SOT_SMD` and `Connector_PinHeader_2.54mm`. Spot-checked, the survivors look genuine (a Cypress QFN-56 whose pads overhang its courtyard by 0.07 mm; an Infineon file listing the same via twice) — consistent with the standing lock that the official library is not a perfectly reliable oracle.

## Phase 4 — EasyEDA is an ingester, and we own the client rather than depending on easyeda2kicad (2026-08-17)

- **Lead.** T1 reads the raw EasyEDA component JSON itself, over stdlib `urllib`, and normalises it into the Part IR. There is **no dependency on `easyeda2kicad`**, vendored or otherwise, and no EasyEDA output ever reaches the user's library: `src/kifab/resolve/easyeda.py` produces `parts/<MPN>.yaml`, and our own emitters rebuild it in house style.
- **Why not depend on it.** Its stable, supported surface is its CLI, and that surface emits the one artefact we have decided not to use — KiCad files. The only parts we would actually consume are its *internals*: a two-URL HTTP wrapper and a KiCad-shaped intermediate model, from a single-maintainer project that promises nothing about them. Reading the JSON directly is ~300 lines, adds **zero runtime dependencies**, and puts the normalisation decisions at the point where the shape strings are parsed, which is the only place they can live.
- **Runner-up: a real dependency**, on the grounds that shape-string parsing is upstream's problem, not ours. It was rejected on the deciding tradeoff that we would be depending on unversioned internals to obtain a *smaller* surface than we ended up writing.
- **Measured, and decisive.** easyeda.com sits behind a CDN that answers **403 to a tool-shaped User-Agent** (`easyeda2kicad v0.8.0` included) and 200 to a browser one. Even the transport is something we would have had to own. MPN -> LCSC-code resolution uses JLCPCB's parts search, because LCSC's own search API is gated and EasyEDA's returns an error for text queries.
- **Degradation path, per the plan.** T1 sits entirely behind the IR. If EasyEDA changes or disappears, `resolve/easyeda.py` is the only file affected and the emitters, validators and corpus are untouched.
- **The suite never touches the network.** Five component payloads are recorded verbatim in `tests/fixtures/easyeda/` (RP2040 LQFN-56+EP, a 0603 resistor, an XC6206 SOT-23, a TL072 SOIC-8, a 1N4007 DO-41), each chosen for a distinct failure mode. `pytest` deselects the single live test by default (`-m live` runs it).

## Phase 4 — Normalise only what is provable; flag the rest in the file itself (2026-08-17)

- **Lead.** Every transformation T1 applies silently is value-preserving and can be argued from the data. Everything else becomes a `# NOTE:` line at the top of the written YAML and, where the linter can prove it, a `kifab check` finding. The two lists are **data** — `easyeda.NORMALISATIONS` and `easyeda.NOT_NORMALISED` — so they are reviewable, and a test asserts every entry states a reason.
- **Normalised, with the argument.** *Pad rotation*: a rect/oval/circle has 180-degree symmetry, so 180 is a no-op and 90/270 is exactly a size swap; 28 of the RP2040's 57 lands arrive that way. Held by `test_folding_pad_rotation_into_the_size_preserves_the_copper`, which checks the result against the **rendered polygon EasyEDA states next to every pad** — the data is its own oracle. *Pin numbers*: read from the drawn number text, never from EasyEDA's header field, which is a sequence index — measured on C5446 (XC6206), where the header runs 1,2,3 while the drawn numbers are 1,3,2, so reading it wires a regulator backwards. *Body size*: taken from the `L…-W…` in the package name (the datasheet body), with the drawn outline used **only** to decide which dimension is which axis — SOT-23 and SOIC-8 carry the same kind of name on opposite axes. *Silk, courtyard and fab*: discarded and redrawn by our emitter. *Multi-gate symbols*: read from `subparts`, because `dataStr.shape` is empty for them and reading it alone yields a pinless symbol.
- **Not normalised, and why.** *Electrical types*: EasyEDA has five against KiCad's twelve and LCSC uses them loosely — a resistor arrives with two `input` pins. Retyping from the pin name is a guess, so the mapping is faithful and SCH002 reports the contradictions it can prove. This is why an imported part typically passes `kifab check` with **warnings** and would fail `--strict`; that is the intended outcome, not a defect. *EasyEDA body sizes that are not stated*: flagged, never invented — its silkscreen is drawn around the pads on a chip package and only between the pad rows on a gull-wing, so it is not a body outline. *Polygon pads*: **refused**, not approximated by a bounding rectangle. *Slotted holes*: imported as a round drill of the stated diameter and flagged. *3D model offset/rotation*: reported, not applied — see the gap below.
- **Chip parts are `custom` by construction.** Two-terminal IPC geometry is not derivable (Phase 1 lock), so an LCSC chip import states its lands directly. That is the escape hatch working as designed, not a shortcut.
- **The IR cross-check is not weakened.** A footprint pad with no symbol pin is an error; `--bond-extra-pads` writes explicitly-unverified `unspecified` pins and says so, mirroring `adopt --pins-from-pads`. A symbol pin with no pad is refused outright — that is EasyEDA's data being wrong at source.
- **Known gap, deliberately left.** EasyEDA states a 3D-model offset and Z rotation (C5446 and C25804 both say `0,0,90`; C2457 says z=-3.5 mm) that `FootprintSpec` has no field for. Adding `model_offset` / `model_rotate` is additive and easy, but it is an IR change and Phase 4 was scoped out of `ir/`. Until then the fact is surfaced as a note rather than silently dropped.

## Phase 4 — Two emitter defects found by the first non-kifab-shaped input (FLAGGED) (2026-08-17)

- **Lead.** Phase 4 was the first tier to feed the emitter geometry it had not generated itself, and it immediately broke the Phase 1 lock that our output is a **fixed point** of `kicad-cli fp upgrade`. Both defects were in `emit/footprint.py`, both are now regression-tested, and both are recorded here rather than patched quietly.
- **Defect 1 — pads must be written in ascending pad-number order.** `fp upgrade` sorts them. Every part in the corpus happened to declare its pads in order already (IPC generates them 1..N), so the emitter never had to. An EasyEDA import states its exposed pad first: the conformance gate reported **222 rewritten lines** on the RP2040. Fixed with a natural sort (`2` before `10`, `A1` before `B1`), stable so a thermal-via variant keeps its relative order. Regression: `tests/test_easyeda.py::test_pads_are_emitted_in_ascending_pad_number_order`.
- **Defect 2 — a through-hole pad carries `(remove_unused_layers no)`.** The corpus was all-SMD until a DO-41 diode arrived from LCSC. Confirmed twice: `fp upgrade` inserts it, and the shipped `Connector_PinHeader_2.54mm` footprints carry it. Regression: the same file's `test_kicad_accepts_and_does_not_rewrite_an_imported_footprint`, which runs the byte-level upgrade gate over all five fixtures.
- **The lesson, which is the reason this entry exists.** Canonical form was established in Phase 0 by diffing the output of *our own generator*, so it could only ever encode the rules our own output happened to exercise. Both rules had been sitting unexercised for three phases. **Any new tier should be run through the byte-level upgrade gate on day one**, not merely through `kifab check`, because `check` reports these as warnings and a warning is easy to read past.
- **No golden file changed.** Neither fix alters the bytes of any existing corpus part, which is the evidence that the fixes are additive rather than a restyle.

## Phase 5 — No-lead (DFN/QFN) is owned; chip still is not, and the missing input now has a name (2026-08-17)

- **Lead.** `ipc/no_lead.py` + IR families `dual_no_lead` / `quad_no_lead` compute DFN/QFN/WSON/UQFN lands from the same three IPC-7351B equations `rules.py` already owned. A no-lead terminal is flush with the body, so `lead_outside = body` (pull-back packages: `body - 2*pull_back`) and `lead_inside = lead_outside - 2L`. Nothing new was invented; the family only changes where the inputs come from.
- **Gated the same way Phase 0b was.** `tests/test_no_lead.py` feeds the dimensions from `vendor/ipc/qfn3x.yaml` and diffs **every numbered land** against the shipped `.kicad_mod`: `QFN-32-1EP_5x5mm_P0.5mm_EP3.45x3.45mm` (square), `QFN-36-1EP_5x6mm_P0.5mm_EP3.6x4.1mm` (rectangular, 8 and 10 lands per side), `QFN-32-1EP_7x7mm_P0.65mm_EP4.65x4.65mm` (larger pitch, exact body). All exact.
- **`pins_x` / `pins_y`, not `pin_count // 4`.** A rectangular QFN carries different land counts on the short and long sides. A generator that divides a total by four gets that silently wrong, and the holdout part is exactly such a package.
- **The exposed pad is stated, never inferred**, and an EP that leaves less than the vendored `min_ep_to_pad_clearance` (0.2 mm) to the nearest land is a hard **error**. kilibs would shrink the lands (heel reduction); refusing is the honest answer until that is implemented and gated.
- **Chip (2-terminal) is still refused — but the blocker is now named.** kilibs computes chip lands with `ipc_pad_center_plus_size(center_position, lead_length)`: the land-centre offset and the termination-band length, from which `S = 2c - T`. That is the input the Phase 1 spike could not find, and the vendored `ipc7351B_2terminal.yaml` states **only fillet goals**, no body or termination corpus. A grid search against the shipped 0402/0603/0805/1206 reproduces `Zmax` and `Xmax` exactly for 0603 and 0805 from IPC-SM-782 body dimensions, but `Gmin` admits **several (T, tolerance) pairs per size** — 0603 fits T=0.30 exact *or* 0.25 +/-0.15; 0805 fits 0.50 +/-0.10 *or* 0.45 +/-0.20. Under-determined is not identified. Chip stays `custom` until a stated corpus exists to gate it against.
- **Also still deferred:** BGA, J-lead, and per-pad overrides (`vendor/ipc/qfn3x.yaml` has entries with `pad_overrides` and `chamfer_edge_pins`; those cases were left out of the gate rather than approximated).

## Phase 5 — model_offset / model_rotate added to FootprintSpec (Phase 4 gap closed) (2026-08-17)

- **Lead.** `FootprintSpec` now carries `model_offset` and `model_rotate`, both `(x, y, z)`, wired straight into the `(model ...)` block. Phase 4 flagged this: EasyEDA states a 90-degree Z rotation for C5446 and C25804 and a -3.5 mm z offset for C2457, and the IR had nowhere to put it.
- **Refused rather than ignored:** stating a placement with no `model` is a validation error. A transform on a model that does not exist is always a mistake, and silently dropping it is how a part ends up 3.5 mm off in every mechanical export.
- **Emitted always, identity or not.** KiCad writes `offset`, `scale`, `rotate` in that order whether or not they are identities, so we do too; the byte-level `fp upgrade` gate in `tests/test_conformance_families.py` holds it.

## Phase 5 — Two more canonical-form defects, found on day one by the byte gate (2026-08-17)

- **Lead.** Phase 4 ended with the instruction to run any new tier through `kicad-cli fp upgrade --force` and a byte diff *on the day it is written*, not through `kifab check` alone. Doing that (`tests/test_conformance_families.py`, written before the family had a single real part) caught two defects immediately. Both were in `emit/footprint.py`; `kifab check` reported neither.
- **Defect 1 — a paste-only pad is numbered `""`.** `fp upgrade` strips the number off any pad with no copper layer. The exposed-pad paste sub-apertures were being emitted carrying the EP number, and every one of them was rewritten. `Pad.aperture` now marks them: they emit with an empty number, are exempt from the IR pin/pad bonding rule (they carry no net), and keep `number` for traceability and for the derived UUID.
- **Defect 2 — pads sharing a number sort by position, x then y.** With the apertures all anonymous, the tie-break became visible: kicad-cli orders them ascending x, then ascending y, and we were emitting row-major. The sort key is now `(pad_order(label), x, y)`. No existing footprint moved — numbers are unique everywhere else, so the tie-break never fires.
- **A latent bug fixed on the way.** UUIDs were derived from the pad number alone, so two pads sharing a number would have carried the same UUID. The seed now counts repeats, with the first occurrence keeping the plain seed so no existing UUID changed.
- **The lesson holds, and it generalises.** Canonical form can only encode the rules our own output has exercised. Every new family, every new emitter field, gets the byte gate before it gets a real part.

## Phase 5 — Three LLM providers behind one interface, and the core stays LLM-free by import (2026-08-17)

- **Lead.** `LLMProvider` has exactly three implementations, selected by `--provider`: `claude-code` (default — runs inside the user's own Claude Code session, so a subscription holder pays nothing extra), `api-key` (BYOK, the user's own Anthropic key at cost) and `none` (`NullProvider`).
- **"The core needs no LLM" is a property of the code, not a claim in a README.** `import kifab.llm` pulls in no SDK and no HTTP client: `ApiKeyProvider` imports `anthropic` lazily inside the call, and `tests/test_llm.py` asserts on a fresh interpreter that `anthropic` is absent from `sys.modules`. T0, T1, T3 and every validator never construct a provider at all.
- **`NullProvider` fails loudly and names the alternatives.** It is the negative control for the whole design: with it selected, `kifab generate` exits 3, writes no proposal, and prints the three tiers that still work (`kifab search`, `kifab lcsc`, hand-written YAML) plus "kifab will not guess pad geometry". A tool that quietly emitted plausible geometry when it could not read the datasheet would be worse than useless.
- **The tool allowlist is a constructor argument, checked.** `EXTRACTION_TOOLS = {read_pdf, emit_ir}`; constructing any provider with anything outside it raises. `ApiKeyProvider` sends **no `tools` key at all**, so the model has no mechanism to read, search or fetch. `ClaudeCodeProvider` translates the allowlist into argv — `--allowed-tools Read`, `--add-dir <sandbox>`, `cwd=<sandbox>`, and `--disallowed-tools` naming Bash/Glob/Grep/WebFetch/WebSearch/Task/Agent/Edit/Write explicitly, so that a permissive user configuration cannot re-open them. `build_argv` is pure and unit-tested; the subprocess run is marked `live`.

## Phase 5 — Deterministic page selection happens before a provider is ever constructed (2026-08-17)

- **Lead.** `kifab.pdf` extracts the text layer locally, scores every page for pin-table and mechanical-drawing evidence, and slices the PDF down to the winners. Only the slice reaches a model.
- **Why it is first, not an optimisation.** It is free, local, deterministic and testable, and it is worth roughly 4x on token cost for a BYOK user (a dense datasheet page runs ~3,600 tokens once it is also rendered as an image). Sending 40 pages also extracts *worse* than sending 8. Doing it after the model call would be paying to discover something a regex already knew.
- **Evidence over keywords where it counts.** Keyword weights are the floor; the discriminating signals are structural — many short lines beginning with a small integer or a BGA designator (pin table), a run of single-letter dimension symbols and toleranced rows, and a JEDEC/JEITA outline reference (drawing). `Selection.explain()` prints the reason per page so a human can see why a page was chosen.
- **Page 1 is always kept**, at a cost of one page: it is the cheapest possible guard against extracting the wrong device from a multi-part datasheet. `MAX_PAGES = 8` is a hard cost ceiling, and the two categories are ranked separately so a document heavy in one cannot crowd the other out.
- **Three refusals, all before the model call.** No text layer (a scanned PDF), no page that looks like a pin table, no page that looks like a drawing — each stops the run and says so. `tests/test_pdf_select.py` runs entirely on hand-built PDFs (`tests/pdfs.py`), so the layer has no test-time dependency on `reportlab` or on any real datasheet.

## Phase 5 — The review gate is structural: generate() cannot write to a library (2026-08-17)

- **Lead.** `generate()` takes `(request, provider, run_dir, conformance, max_pages)`. There is **no argument you could pass it** that names a library or a parts directory, and a test asserts that parameter set. It stages everything under `runs/<MPN>/`.
- **`review.accept()` is the only writer into `parts/`,** and it is reachable only from a separate command a human types (`kifab accept runs/<MPN>/`). Before it copies anything it re-runs `load_part`, the full validator, and the transcript audit, and refuses on any error. A reviewer who is not looking carefully still cannot promote a part that fails `kifab check` or whose provenance is unproven.
- **The gate must be see-through to be real.** A proposal carries the IR YAML, a built `.kicad_sym`/`.kicad_mod`, an SVG preview rendered by `kicad-cli`, the page-selection rationale, and every `# NOTE:` the model wrote, hoisted out of the YAML so they are read rather than scrolled past.
- **A reply that fails to parse is still written to disk** before it is parsed, so a failed run leaves something a human can read instead of a stack trace.
- **The MPN is ours, not the model's.** A reply that renames the part has its `mpn` overwritten with the one the run was started for — it keys every derived UUID, and a renamed part is a file nobody asked for.

## Phase 5 — Blind-holdout isolation: structural first, audited second — and one layering fix to make it true (2026-08-17)

- **Lead.** The T2 code path is constructed from `(datasheet PDF bytes, MPN string)` and nothing else. `GenerationRequest` has exactly two fields; `ExtractionRequest` adds only the selected page numbers and the instruction text. The library index is owned by T0 and is **not in the import graph**: `tests/test_generate.py` runs a fresh interpreter, imports `kifab.generate`, and asserts no `kifab.index.*` or `kifab.resolve.*` module is present.
- **That assertion failed when first written, and the fix is a genuine layering repair.** `validate/parse.py` imported `unquote` from `index/read.py`, which dragged the whole local-library layer into every validator and therefore into T2. `unquote` now lives in `emit/sexpr.py` next to `quote`, whose exact inverse it is; `index.read.unquote` re-exports it. One misplaced helper was the only thing standing between the claim and the property.
- **The sandbox is the second structural layer.** Every provider is constructed with a `Sandbox` rooted at `runs/<MPN>/scratch`. Any path that resolves outside it is refused, and `*.kicad_mod` / `*.kicad_sym` / `*.pretty` are refused **even inside it** — no legitimate extraction reads an existing footprint. Refusals are recorded; a refusal in the transcript is evidence the constraint fired, not a violation of it.
- **The audit is the proof, and it is a deliverable.** Every provider call, sandbox access and refusal appends to `runs/<MPN>/transcript.jsonl`. `kifab audit runs/<MPN>/` prints the trace and asserts **zero** of: a read of any `*.kicad_mod`/`*.kicad_sym`/`*.pretty`; a fetch matching `snapeda|snapmagic|ultralibrarian|componentsearchengine|lcsc|easyeda`; a *successful* access outside the run scratch directory. Locations are checked in `path`, `file`, `url`, `target`, `source`, `argv` and `command`, so a library path hidden in a command line is caught too. Any violation fails the run regardless of output quality, and `accept()` refuses a run that fails the audit.
- **A missing or empty transcript is a failure, not a pass.** No record is not the same as a clean record. An unparseable line fails too — a line the auditor cannot read is more suspicious than one it can, so it is surfaced rather than skipped.
- **The auditor has been made to fail.** `tests/test_audit.py` stages each violation class (a library read, six aggregator URLs, an escape from the scratch dir, a library path buried in `argv`) and asserts it is caught. An auditor that has never rejected anything is not evidence.
- **The harness knows no LTC5552 geometry, and that is enforced.** `tests/test_blind_holdout.py` asserts: no `parts/LTC5552*` or golden file exists; no source file states a millimetre-shaped figure within three lines of naming the part; and — guarding the guard — the harness file itself contains **no decimal literal at all**. The live run is marked `live` and needs `KIFAB_LTC5552_DATASHEET`; `scripts/blind_holdout.sh` runs it in a scratch tree containing only the datasheet, audits it, validates it, and prints the grading checklist. Grading against ADI drawing 05-08-1985 is a human step with `scripts/grade_footprint.py` (a pure two-file comparator, +/-0.05 mm, with `--not-identical-to` for the trap footprint) because the tolerance and the answer must not live in this repository.

## Phase 6 — Parts are identified in Part-DB by MPN; the state file records what we wrote, not who we are (2026-08-17)

- **Lead.** `kifab sync` looks a part up by `?manufacturer_product_number=<MPN>` on every run. It does not trust a locally remembered row id, and it does not stamp a kifab-owned key onto the inventory.
- **Why not a kifab-owned `ipn`** (`kifab:<library>:<mpn>`). Unambiguous, and Part-DB enforces its uniqueness — but it only ever matches rows kifab created. The real workflow is that the inventory row already exists, because somebody bought the chip before anybody drew it. A sync that cannot see those rows creates a duplicate of every part the user already owns, which is precisely the failure 'idempotent' is supposed to exclude. It also consumes a user-visible field they may already have a scheme for.
- **Why not a local state file as the identity.** Lose it, or sync from a second machine, and every part is created again.
- **What the state file (`partdb-sync.json`) is then.** A record of the exact values kifab last wrote to the four EDA fields, per instance, keyed by MPN. It is a drift detector, never the identity. It is what lets sync distinguish 'the server differs from what we want and equals what we wrote' (our change — update) from 'the server differs from both' (somebody edited it — conflict, report, change nothing). It carries no timestamps and sorts its keys, so two identical syncs produce byte-identical files; it is meant to be committed.
- **Ambiguity is reported, never resolved.** Two rows sharing an MPN is a fact about the user's inventory. A library generator picking one is a guess with inventory consequences.
- **Case.** Part-DB filters that field with SQL `ILIKE`, so the match is case-insensitive; kifab re-checks results case-folded rather than case-sensitively, because a case-sensitive re-check would reject a legitimate match and then create a duplicate.

## Phase 6 — kifab owns four EDA fields in Part-DB and nothing else (2026-08-17)

- **Lead.** On update, `kifab sync` writes exactly `eda_info.kicad_symbol`, `eda_info.kicad_footprint`, `eda_info.reference_prefix` and `eda_info.value`. Nothing else, ever. On create it additionally fills name, description, MPN and `manufacturer_product_url`, because a new row has to have them.
- **Why.** Stock, storage bins, prices, suppliers, attachments and the user's own description are inventory data that people maintain by hand. A library generator overwriting them destroys work that cannot be regenerated from `parts/`. The symbol and footprint pointers can always be regenerated; that asymmetry is the whole rule.
- **The datasheet does not reach KiCad this way.** Part-DB builds KiCad's `datasheet` field from *attachments*, which kifab does not manage. The URL is written to `manufacturer_product_url` on create for the human reading the inventory row, and that is all it does. Recorded so nobody later 'fixes' it by writing to the wrong field.
- **Part-DB requires a category.** `kifab sync` resolves a category by name and creates it if absent (default `kifab`), rather than demanding the user look up a numeric id before their first run.

## Phase 6 — Two Part-DB API surfaces, two modules — and the two traps in them (2026-08-17)

- **Lead.** `partdb/client.py` speaks the **Part-DB REST API** (`/api/…`, API Platform, `Bearer tcp_…`) and is how kifab *writes*. `partdb/httplib.py` generates the `.kicad_httplib` that points at the **KiCad HTTP library API** (`{instance}/en/kicad-api/` + `v1`) and is how *KiCad reads*. kifab never calls the second one. Keeping them in separate modules is deliberate: conflating them is the mistake that makes people think Part-DB is a geometry source.
- **Trap 1 — `eda_info` is serialised on `GET /api/parts/{id}` only, not on the collection.** Part-DB's item operation adds the `eda_info:read` group; the resource-level context used by `GetCollection` does not. A sync that compared against the collection row would see four empty fields on every run and PATCH forever, looking correct in a demo and generating unbounded changelog noise in production. `plan_sync` therefore re-reads the matched part as an item. `tests/partdb_fake.py` reproduces the split on purpose, and `test_the_collection_gap_does_not_cause_perpetual_updates` fails if the re-read is removed.
- **Trap 2 — `root_url` must stop before `v1`.** KiCad concatenates `api_version` onto `root_url`. Pasting the full `/en/kicad-api/v1` produces `/v1/v1/…`, and KiCad reports no error — the library is simply empty. `kicad_api_root()` strips a pasted `v1` back off and keeps the trailing slash.
- **All values KiCad receives must be strings.** That is why `DesiredPart` is entirely `str`; a fixture test asserts every leaf of a recorded KiCad response is a string, so a field typed as int or bool fails a test rather than a KiCad import.
- **stdlib `urllib`, injectable transport, no retries.** As with the EasyEDA client: four endpoints do not justify an HTTP dependency in a library-generation tool. No retries because sync is idempotent — the right answer to a transient failure is to run it again, and a client that silently retries a POST is how duplicate inventory rows appear.
- **Verified by fixture, not against a live server.** Docker's daemon was not running on the development machine, so nothing here has ever spoken to a real Part-DB. The fixtures are transcribed from Part-DB v2.15.0's entity definitions and documented responses; `test_against_a_real_partdb_instance` is marked `live` and is the acceptance test that has not been run.

## Phase 7 — Three distribution channels, and the artefact gate that keeps them honest (2026-08-17)

- **Three doors, deliberately different audiences.** The Claude Code plugin is the primary channel (the LLM runs on the user's own subscription — no key, no credits, no bill to us). `uvx kifab` is the deterministic core for CI and non-Claude users. The PCM feed publishes the *output*, so a designer can subscribe to the library from inside KiCad and never run the tool. None of the three costs anything to operate and none needs a paid domain.
- **`scripts/wheel_smoke.sh` is a gate, not a convenience.** Every test in the repo runs with `src/` on `sys.path`, which structurally cannot catch a data file present in the checkout and absent from the wheel — the failure that works in-repo and dies on a stranger's first `uvx kifab`. The smoke script builds the wheel, installs it into an empty venv, `cd`s outside the repo and runs real commands. It asserts: every non-`.py` file under `src/kifab/` is in the wheel, `load_rules()` and `find_schema()` both work from site-packages, `anthropic` is *not* pulled in by a plain install, and the T2 import graph is still clean in the installed package. It runs in `verify.sh` and again in CI before any upload.
- **KiCad's `pcm.v1.schema.json` is vendored *into the package*, not into `vendor/`.** A `uvx` user has no checkout and CI has no KiCad; a validator reachable only from a source tree is a validator that never runs where it matters. `find_schema()` still prefers an installed KiCad's copy, so a KiCad 10 schema change surfaces the day the user upgrades.
- **The PCM archive is byte-reproducible.** Fixed zip timestamps, sorted entries, fixed mode. A rebuild that changed no part must produce the same sha256, or every CI run shows subscribers an Update button that updates nothing — the fastest way to teach people to ignore the Update button.
- **The PCM version is the library's, not kifab's**, and defaults to the UTC date. The corpus changes when somebody adds a part, not when the tool is released. Known limitation: two publishes on the same day collide, and need an explicit `--pcm-version`.
- **Trusted publishing (OIDC), never a stored token.** `publish.yml` has `id-token: write` and references no secret at all. The one-time PyPI pending-publisher setup is documented in the workflow header rather than in someone's memory.
- **The licence is GPL-3.0-or-later, and this was a finding, not a preference.** `src/kifab/ipc/ipc_7351b.yaml` is derived from the KiCad Librarian Team's `generators` repo (GPLv3+) and `toleranced.py` mirrors its `TolerancedSize` maths. A permissive licence would have been a false claim about that lineage. The *library* kifab publishes is labelled `CC-BY-SA-4.0` — matching KiCad's own libraries — because symbols and footprints are content that ends up in other people's boards. Two different questions, two different answers.
