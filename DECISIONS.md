# Decisions

Locked decisions that should not be silently relitigated. Newest last.

---

## 2026-08-17 — Phase 0a: own the S-expression emitter (GATE PASSED)

**Decision.** Build and own the S-expression parser/writer. Do not depend on
`kiutils` or `KicadModTree`.

**Evidence.** `src/kifab/emit/sexpr.py` + `tests/test_roundtrip.py`, run against
the KiCad 9.0.4 install:

- Semantic round-trip (no data loss) on **400 footprints + 10 symbol libraries** — pass.
- Byte-exact idempotence on **400 footprints** — pass.
- Byte-exact on every node shape we generate — pass.
- `kicad-cli fp upgrade --force` accepts our output (exit 0); `fp export svg` renders it.

**Measured limitation, accepted deliberately.** We do *not* byte-match arbitrary
third-party files. KiCad's shipped libraries are not uniformly formatted (written
by several generators over many years), and even within `kicad-cli`-canonicalised
output the `pts` packing rule could not be reduced to a consistent formula: across
486 width-bound samples the longest line KiCad *kept* was 122 chars while the
shortest it *rejected* was 113, so it is not a pure column limit. The only clean
invariant found was a hard ceiling of **8 points per line**.

This is not a requirement of anything in the project. The requirements are no data
loss (enforced across the corpus) and `kicad-cli` acceptance (enforced per build).

## 2026-08-17 — `kicad-cli fp upgrade` is a canonicaliser, not just a validator

**Decision.** Treat `kicad-cli` as the source of truth for canonical KiCad 9 form,
and encode its rules in the emitter rather than guessing them.

**Why.** Feeding it a minimal hand-written footprint and diffing what came back
produced the canonical-form spec directly. Rules it enforced:

| Rule | Detail |
|---|---|
| `generator_version` | `(generator_version "9.0")` is required alongside `(generator ...)` |
| Mandatory properties | All four of Reference, **Value, Datasheet, Description** always present, even when empty |
| UUIDs | Every property, `fp_line`, `fp_poly`, and `pad` carries a `(uuid ...)` |
| Pad layer order | Canonical order is `"F.Cu" "F.Mask" "F.Paste"` — **not** Cu/Paste/Mask |
| Trailer | `(embedded_fonts no)` closes the footprint |
| `attr` placement | Moves to after the property block |

## 2026-08-17 — Phase 0b: own the IPC-7351B maths (GATE PASSED)

**Decision.** Implement IPC-7351B land-pattern calculation ourselves, vendoring
KiCad's rule *data* (`ipc_7351b.yaml`) but not their code. Proceed with the
IR-centric architecture; do **not** fall back to vendoring the generator wholesale.

**Evidence.** `src/kifab/ipc/` + `tests/test_ipc.py`. Fed the same input dimensions
the KiCad library team publishes, our computed land geometry matches the shipped
footprints **exactly** (≤1e-4 mm) across three IPC device classes:

| Package | Class | length × width @ centre |
|---|---|---|
| LQFP-48_7x7mm_P0.5mm | gullwing, small pitch | 1.475 × 0.30 @ 4.1625 |
| SOIC-8_3.9x4.9mm_P1.27mm | gullwing, large pitch | 1.95 × 0.60 @ 2.475 |
| QFN-32-1EP_5x5mm_P0.5mm | flat no-lead | 0.875 × 0.25 @ 2.4375 |
| SOT-23-5 | gullwing, large pitch | 1.325 × 0.60 @ 1.1375 |

**Recovered constants.** IPC's fabrication allowance **F = 0.10 mm** and placement
allowance **P = 0.05 mm** are not stated in any upstream config file. They were
recovered by solving against LQFP-48 and then confirmed against every other case
above. They live in `kifab.ipc.rules` as named constants so drift surfaces as a
test failure rather than silently wrong pads.

## 2026-08-17 — The official library is NOT a perfectly reliable oracle

**Decision.** When computed geometry disagrees with a shipped footprint,
investigate before assuming our arithmetic is wrong. Compare against the inputs
the footprint was *generated from*, not merely the current size definitions.

**Why.** `SOT-23` does not match its own current size definition. Feeding today's
`sot.yaml` (`lead_len: 0.40 .. 0.60`) gives Gmin=0.35; the shipped footprint
implies Gmin=0.40. Feeding `lead_len: 0.40 .. 0.55` reproduces the shipped file
exactly — so it was generated before that dimension was revised and never
regenerated. `SOT-23-5`, generated by the same script, matches us perfectly.

**Consequence.** Kept as `test_shipped_sot23_is_stale_not_our_maths` rather than
deleted, so the reasoning stays in the suite. If upstream regenerates SOT-23 the
test fails and tells us to promote it back into the main comparison set.

## 2026-08-17 — UUIDs are derived, never random

**Decision.** Generate every `(uuid ...)` deterministically as a UUIDv5 over
`(part identity, element kind, element index)`. Never call `uuid4()`.

**Why.** KiCad requires UUIDs on most elements, but random ones make output
non-reproducible: the same IR would emit a different file on every run, so
golden-file tests could never be byte-compared and every regeneration would show
a spurious diff in git. Deriving them keeps the pipeline a pure function of the
IR, which is what makes the golden-file gate meaningful.

**Consequence.** Two different parts never collide (identity is in the hash), and
regenerating an unchanged part is a no-op in version control.
